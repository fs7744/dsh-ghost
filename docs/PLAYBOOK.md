# 剧本（Playbook）

> 一句话：**剧本就是 skill。人看流程图，模型读紧凑文本；复杂 JSON 只活在 UI 缓存里，永不进 prompt、永不进 git。**

## 1. 为什么分两种表示

同一张流程图有两个消费者，需求相反：

| 消费者   | 需要的                  | 不需要的          |
| ----- | -------------------- | ------------- |
| 人（UI） | 节点位置、连线、分支标签、折叠、主题   | ——            |
| 模型    | 按什么顺序做、什么条件转哪、最多重试几次 | 坐标、UUID、样式、视口 |

**实测（同一条 10 节点流程）**：

| 表示                             | 字符    | 估算 token |
| ------------------------------ | ----- | -------- |
| `.flow` 文本                     | 301   | **109**  |
| 完整 UI JSON（节点坐标 + 边 + 视口 + 样式） | 3,342 | 945      |

**8.7 倍**。而且文本的 diff 是一行一句人话，JSON 的 diff 全是坐标噪音。

## 2. 语法

```
# @<id> v<版本>
# when   <触发条件，一行>
# goal   <验收目标，一行>
# budget <可选配额，如 轮次<=3 工具<=40>

<节点>                                  # 顺序执行
<节点> : <条件> -> <目标> [(max n)]      # 条件跳转
?<节点>                                 # 需要人确认的闸门
call <子剧本id>                          # 子流程调用
```

规则：

1. 空行与 `#` 注释忽略；缩进无关。
2. **节点名就是跳转 id**，不需要 UUID；重名报错。
3. 默认边 = 顺序边（上一节点 → 下一节点）。`->` **只写例外**：拒绝、失败、阻塞、回退。
4. `(max n)` 限定该回边最多走 n 次，超出后落到顺序的下一节点。
5. 最后一个节点默认结束。

这就是省 token 的三条根本原因：**顺序即边**（省掉整个 edges 数组）、**条件内联**（省掉条件节点）、**名字即 id**（省掉 id 映射表）。

## 3. 示例：superagent 的 Ticket 流程

```
# @ticket-flow v2
# when 源收到对 agent 的请求（issue 评论 / 群提及）
# goal 在该仓库产出可审阅结果（PR 或答复）
# budget 准入1 执行3轮 每轮工具<=40

admit       : deny -> quiet
open-ticket
checkout
work        : blocked -> escalate (max 3)
verify      : fail -> work (max 2)
deliver     : pr-ready -> open-pr
open-pr
reply
close
quiet
escalate
```

11 行、约 110 token，把"准入 → 开工 → 检出 → 干活 → 验证 → 交付 → 收尾"，外加"拒绝就沉默""阻塞就升级""验证失败返工两次"全部说清。

## 4. 图 ↔ 文本的同步规则

- **唯一真相源是 `.flow` 文本**。图是它的视图，布局 JSON 是视图的缓存。
- 打开：`parse(.flow)` → 自动布局（纵向，dagre/elk）→ 渲染。
- 拖动节点：**只写布局缓存**，文本一字不改。
- 改标签 / 加条件 / 连线 / 删节点：**改文本** → 重新 parse → 重绘。
- 布局缓存：`.ghost/cache/layout/<剧本id>.json`，**gitignore**，不进仓库。
- Diff：给文本 diff（人可读）；图里高亮新增/删除/改标签，仅作辅助。

单向数据流是这套设计不发抖的原因：**图永远不直接改语义**。

## 5. 编辑器：只用鼠标，零语法

**用户永远看不到 `.flow` 语法。** 语法是编译器的事。界面上只有两样东西：**动作块**和**线**。

### 5.1 全部编辑动作只有五个

| # | 动作      | 怎么操作              | 用户看到什么                               |
| - | ------- | ----------------- | ------------------------------------ |
| 1 | **加一步** | 从底部「步骤架」拖一个圆角块到画布 | 块里只有一条空横线：*这一步做什么？* 点一下打一句话          |
| 2 | **连起来** | 拖块底部的圆点，松手到另一个块   | 圆角正交线；**不拖也行**——新块自动吸在上一个块下面并自动连好    |
| 3 | **加条件** | 点块右上角的「如果…」       | 一个下拉：成功 / 失败 / 被拒 / 卡住 / 自定义；选完拖线到目标 |
| 4 | **设重试** | 点线中间那个「×2」        | 加减号或直接输 1–9                          |
| 5 | **加人闸** | 点块左上角的开关          | 块上出现斜纹边：这一步要人点头                      |

删除 = 拖回步骤架（或选中按 Delete）。撤销 = `Ctrl+Z`，**但界面上也有撤销按钮**——不能要求人记快捷键。

### 5.2 「小孩子都能懂」的具体做法

- 块上写**动词短语**（"读仓库""改代码""跑测试"），永远不出现标识符、括号、箭头符号。
- 颜色只表达**状态**：灰=没跑、蓝=正在跑、绿=成功、红=失败。不用颜色区分类型。
- 连线只有一种样式；唯一的额外符号是条件标签和重试数字。
- **没有任何输入框要求格式**：不填语法、不填 id、不填坐标。
- 第一次打开有 3 步引导：拖一个块 → 连一根线 → 点运行。

### 5.3 三条数据铁律（保证"图不会抖"）

1. **图模型 → 文本**：每次编辑立刻序列化，防丢。
2. **文本 → 图模型**：只在文本被外部改动时（专家模式、`git pull`、AI 直接改文件）。
3. **布局缓存 → 只影响渲染**：拖动节点永不触发重新序列化。

> 高级用户可展开「查看文本」，此时是专家模式，改文本反向解析回图。默认收起——语法是逃生门，不是主入口。

## 6. AI 生成与编辑

同一个画布，两个入口，产出同一份图模型。

### 6.1 生成

空画布中央一个输入框：*你想要什么流程？* 一句话 → 节点**流式逐个出现并自动连线** → 生成完直接进入可编辑状态。

生成的是**图**，不是文本；文本由序列化得到。所以"AI 生成的"和"手拖的"没有区别，之后照样拖、照样改。

### 6.2 编辑

选中（一个块 / 一条线 / 框选一段）→ 右键「让 AI 改」→ 说一句"失败后重试两次" → **只重写该局部**。

关键约束：**局部重写保留布局**。不做整图重排，否则用户刚摆好的位置会被冲掉——这是这类编辑器最容易毁体验的地方。

### 6.3 AI 产物必须过同一道校验

- AI 只能产出 `.flow` 文本或图模型 JSON，两者走**同一套校验**（悬空跳转 / 不可达 / 重名 / 缺 goal / 回边无上限）。
- 校验不过**不落盘**：界面上把出问题的那个块标红，并用人话说哪里不对。
- 通路和手改完全一致：文本 → 校验 → 图模型 → 画布。

### 6.4 反向：AI 读的不是图

模型拿到的永远是编译好的 skill（第 7 节），不是图 JSON。这条**不能破**——一破，token 就白省了。

## 7. 编译产物：一个完整的 skill 包（不是一篇文档）

剧本编译出来的是 **skill 包**，对齐 Anthropic Agent Skills 的目录约定：

```
playbooks/ticket-flow/
├── SKILL.md          # 必需：frontmatter(name, description) + 流程图正文（编译自 .flow）
├── flow.flow         # 源：唯一真相源
├── scripts/          # 确定性步骤写成可执行脚本（省 token 的主力）
│   ├── admit.mjs
│   ├── verify.mjs
│   └── deliver.mjs
├── references/       # 按需读的长文
│   ├── nodes/        #   节点详情：<节点名>.md（有才生成）
│   ├── delivery.md
│   └── policy.md
└── assets/           # 模板：PR 模板、提交信息模板
```

### 7.1 四级加载（每级都比上一级贵得多）

| 级 | 内容 | 何时进上下文 | 量 |
|---|---|---|---|
| L1 | 元数据（name + description） | 常驻 | ~20 token |
| L2 | `SKILL.md` 正文（流程图 + 每步一句） | 模型调用该 skill 时 | ~110–200 |
| L3 | `references/*.md` | 模型明确需要时读单个文件 | 400–600 / 文件 |
| L4 | `scripts/*` | **只跑不看**——进上下文的是输出 | 40–80 / 次 |

### 7.2 脚本优先：把确定性从模型挪到代码

这是"多用脚本省 token"的机制，不只是省字数：

| 同一个"怎么验证"步骤 | 常驻成本 | 单次成本 |
|---|---|---|
| 写在提示词里描述步骤 | 400–600 token（一直占着） | —— |
| 放进 `references/verify.md` 按需读 | 0 | 400–600 |
| 写成 `scripts/verify.mjs` 跑一次 | 0 | **输出 40–80** |

五条硬规则：

1. **能写成脚本的，不写成说明**。凡是"按固定步骤做 / 校验 / 格式化 / 查询"，一律进 `scripts/`。
2. **输出即上下文**。模型只看到 3–10 行结构化结果，看不到 200 行实现。
3. **失败要自解释**：脚本失败返回 `{ok:false, code, fix, hint}`，模型不必读源码、不必翻文档。
4. **`--help` 只输出一行摘要**，供模型判断要不要用；详细用法放 `references/`。
5. **幂等、无交互**：不接受 stdin 提问、不弹确认、可重复执行。

> 判断标准很简单：**这一步需要模型"判断"吗？** 需要 → 留在剧本里当节点；不需要 → 写成脚本。

### 7.3 实测：编译后的真实 token

`ticket-flow`（11 节点）编译产物：

| 项 | 量 |
|---|---|
| 常驻 description | **37 token** |
| 按需正文（流程图） | **48 token** |
| 两者合计 | **85 token** |
| 同流程的完整 UI JSON（坐标 + 样式 + 视口） | **685 token** |

正文对 JSON 是 **14.3 倍**；算上常驻的 description 也有 **8 倍**。这就是"文本给模型、JSON 给 UI"的收益。

### 7.4 节点详情：二次按需

作者在剧本同目录放 `nodes/<节点名>.md`，编译时会：

1. 生成 `references/nodes/<节点名>.md`
2. 在 `SKILL.md` 对应节点的行尾加一个指针：`verify : fail -> work (max 2)  → references/nodes/verify.md`

实测：`ticket-flow` 只有 `verify` 一个节点有详情，正文从 48 → **56 token**（8 token 换"按需可查"）。没有详情的节点一点不变。

### 7.5 节点与脚本的对应

剧本节点上可以挂一个脚本（可选）：

```
admit  : deny -> quiet            @scripts/admit.mjs
work                                  # 无脚本：纯模型执行
verify : fail -> work (max 2)     @scripts/verify.mjs
```

- 有 `@script` 的节点：模型执行 = 跑脚本 + 读输出，几乎不耗 token。
- 没 `@script` 的节点：模型自己干（写作、判断、改代码）。
- 两者在图上长得一样，只是一个带「脚本」小标签——**这个细节不给用户看**，用户只看到"这一步做什么"。

## 8. 校验（编译期 fail fast）

- 跳转目标不存在（悬空）
- 不可达节点
- 节点重名
- 缺 `goal`
- 回边没写 `(max n)`
- 条件为空、子剧本不存在
- `@script` 指向的文件不存在、或不可执行
- `SKILL.md` 的 `name` / `description` 缺失或超长（描述是常驻成本，必须短）

校验不过 → 不生成 `SKILL.md`。不允许"写着玩的剧本"上线。

## 9. 迁移：superagent 现有 14 个提示词怎么办

| 现有内容                                             | 归属                     |
| ------------------------------------------------ | ---------------------- |
| 角色与语气（`worker.md` / `orchestrator.md` 的身份段）      | 保留为 persona，短、常驻       |
| 流程与步骤（`dispatch.md` / `handoff*.md` / `work.md`） | **改成 `.flow` 剧本**，按需加载 |
| 判断标准与禁忌（`team/*.md` / `replies.md`）              | 节点详情或 shared 段         |

预期效果：常驻系统提示从数千 token 降到数百，流程细节变成按需付费。**这本身就是省钱，不只是省 token。**

## 10. 不做

- 不做 BPMN 全套（泳道图、事件网关、补偿事务）——只保留：步骤 / 条件 / 回退 / 人闸 / 子流程。
- 不做多人协同编辑。
- 不把布局、主题、视口写进仓库。
- 不允许图与文本各存一份（那必然不一致）。
